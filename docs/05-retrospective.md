# 05 · 复盘

## 最难的问题

**1. 让"观察超预算 → 调整"真实发生，而不是被预判跳过。**
最初实现里，Mock 用 `feasible` 过滤直接排除了超预算方案 —— 结果它"绕过"了 premium，
从没真正**观察到**超预算事实。Trace 看着像完成了，但恰好漏掉了本题的核心验收点
（模型据工具结果调整）。改成"先估首选方案、观察 over_budget 事实后再改选替代"后，
Trace 才真实体现决策链。教训：**决策必须由"观察到的结果"驱动，不能由"提前知道的答案"驱动**——
否则 ReAct 就是假的。

**2. 工具失败后的状态一致性。**
最省事的做法是失败就整体重来或整体放弃，都会丢结果或死循环。正确做法是让**步骤状态正交**：
失败步骤标 `failed`，已成功步骤保留 `success`，模型据此决定续跑还是停止。
数据结构（`Step.status`）选对了，失败处理逻辑自然成立。

**3. 续跑不能重做已完成的活。**
续跑若从头执行，等于"失败重试"而非"失败续跑"。解法是把上次已成功步骤的动作+观察
注入对话历史，模型看到事实后自然跳过。trace 里 `search_materials`/`estimate_cost` 不再出现，
就是证据。

## 学习收获

- **好品味 = 状态正交**：把 `pending/success/failed/skipped` 拆开，失败处理、续跑、
  费用计算三件事全都自然成立，不需要额外分支。
- **验证要"真"**：Trace 必须逐行核对是否真的体现"观察→调整"。这次就是靠核对才发现
  Mock 预判跳过了核心步骤。
- **无解要诚实**：预算不足时返回 `incomplete` + 缺口，比硬凑一个方案更有价值。

## 下一步

1. **接真实模型跑一轮**：对比真实 LLM 与 Mock 的决策差异，重点看模型是否会"突破预算"—
   这是最需要防的（prompt 已写硬约束，但需实测）。
2. **续跑落 CLI**：暴露 `--resume-from <state.json>`，让失败续跑可通过命令行演示。
3. **成本模型细化**：按工具逐项累加，建模截止时间约束（耗时是否赶得上）。
4. **持久化 + 并发**：`PlanStore` 换成带唯一索引的存储。
5. **多方案批量**：一次规划为多个主题产出方案。
